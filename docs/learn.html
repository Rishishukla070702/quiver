① The 30-second big picture

What does Quiver actually do?

It stores vectors (lists of numbers that capture the meaning of things) and, given a query, finds the most similar stored vectors — fast, even over millions. That powers semantic search, recommendations, and RAG.

TEXT ─► [embedding model] ─► VECTOR ──────────────► stored in the INDEX ▲ QUERY TEXT ─► [same model] ─► QUERY VECTOR ──► SEARCH ┘ ─► k most similar ─► results

Everything else in this guide is a zoom-in on one box of that diagram.

② Vectors & embeddings

The raw material.

Vector jargon

An ordered list of numbers, e.g. [0.12, -0.03, 0.88, …]. Geometrically, a point (or arrow) in space. In Quiver:

type Vector []float32   // float32, not float64 — half the memory for millions of vectors

Jargon: vector = the list of numbers · dimension = how many numbers it has.

Dimension jargon

The length of the vector — how many numbers. [1,0] is 2-dimensional; a real text embedding is often 384-dimensional. Think coordinates: (x,y) is 2-D, (x,y,z) is 3-D. Every vector in one index must share the same dimension.

Embedding & embedding model jargon

An embedding is a vector produced by a neural net (the embedding model) trained so that things with similar meaning land at nearby points. "meaning becomes geometry." Quiver's demo uses all-MiniLM-L6-v2 (outputs 384-dim). Quiver doesn't build the model — it stores and searches its output.

🤔 Check yourself: why must the query and the stored vectors use the same model & dimension?
Because similarity is measured component by component (position 42 vs position 42). That's only meaningful if both vectors live in the same space — same size, and same model, since each position means the same learned feature only within one model. Mismatched size → Quiver returns ErrDimMismatch and refuses to compute nonsense.

③ Distance / similarity metrics

How do you measure "how similar are two vectors?"

Dot product jargon

Multiply matching components and sum them: a[0]*b[0] + a[1]*b[1] + …. The primitive the other metrics are built from.

func Dot(a, b Vector) (float32, error) { /* sum a[i]*b[i] */ }
L2 / Euclidean distance jargon

Straight-line distance: sqrt(sum((a[i]-b[i])²)). Smaller = more similar (0 = identical). The everyday "how far apart" ruler distance. Used by the SIFT benchmark.

Cosine similarity jargon

The cosine of the angle between two vectors: Dot(a,b) / (‖a‖·‖b‖). Range −1…1: 1 = same direction, 0 = unrelated, −1 = opposite. It compares direction, ignoring magnitude — which is why it's the default for text (meaning is in the direction; length is noise).

Jargon: magnitude / norm (‖v‖) = a vector's length = sqrt(sum(v[i]²)) · metric = the chosen similarity function.

Why compare floats with an epsilon go

Operations like sqrt introduce tiny rounding, so a "true" 1.0 might be 0.99999994. You never test floats with ==; you check "within a tiny tolerance ε." (Exception: comparing to exactly 0 for a sum-of-squares is fine — it's 0 only if every term is 0.)

🤔 Check yourself: two docs on the same topic, one long, one short — which metric calls them similar, cosine or L2?
Cosine. A long and short doc on the same topic point the same direction but have different magnitudes (length). Cosine ignores magnitude → high similarity. L2 would see them as far apart because of the length difference. That's why text search uses cosine.

④ The index & top-k search (FlatIndex)

The simplest way to answer a query — correct, but slow.

Index jargon

The structure that stores vectors and answers "find the k most similar." Quiver has two: FlatIndex (exact) and HNSW (fast/approximate).

Brute force & O(n) jargon

FlatIndex compares the query against every stored vector. That's O(n) ("order n"): the work grows linearly with the number of vectors n. 10× the data → 10× the time. Exact, but doesn't scale.

Jargon: Big-O = how cost grows with input size · brute force = check everything · k-NN = k nearest neighbors.

top-k & the search flow

top-k = return the k best matches. FlatIndex's Search: validate the query dimension → score every vector → sort best-first → return the top k. It's also Quiver's correctness oracle: its exact answers are what we grade the fast index against.

🤔 Check yourself: why is FlatIndex "exact," and why won't it scale?
Exact because it literally checks every vector — it can't miss the true nearest. Won't scale because that's O(n): at a million vectors every single query does a million comparisons. HNSW (§6) fixes the scaling by checking only ~log(n) of them.

⑤ Interfaces & abstraction

How the server runs either index without caring which.

Interface (the Go kind) go

An interface is a set of method signatures — a contract. Quiver's:

type Index interface {
    Add(id string, vec vector.Vector) error
    Search(query vector.Vector, k int) ([]Result, error)
    Len() int
}

The Go twist: satisfaction is implicit — no implements keyword. Any type that happens to have those methods satisfies the interface automatically. So *FlatIndex and *HNSW both satisfy Index without any change to them.

Jargon: implicit / structural typing = "if it has the methods, it fits" · dependency inversion = depend on the contract, not a concrete type.

Decorator pattern

PersistentIndex (§9) wraps an Index, adds durability, and is itself an Index. So you can slip it in front of the real index and nothing downstream notices. That's the decorator pattern — and it only works because of the interface.

🤔 Check yourself: how does one server.New(idx) accept both FlatIndex and HNSW?
Because New takes an index.Index (the interface), not a concrete type. Both *FlatIndex and *HNSW have Add/Search/Len, so both satisfy Index implicitly. main.go picks one via the -index flag; the server just sees "an Index."

⑥ ANN & HNSW — the heart

Checking ~log(n) vectors instead of all n. (Full visual: docs/hnsw.md.)

ANN & recall jargon

ANN = Approximate Nearest Neighbor. Trade a sliver of accuracy for a huge speed win. "Approximate" means it might miss a true neighbor occasionally — measured by recall.

recall@k = of the k true nearest (per the exact index), what fraction did we find? 0.99 recall@10 = "found ~9.9 of the true top 10."

Proximity graph & greedy search jargon

Put vectors in a graph: nodes = vectors, edges connect near neighbors. To search, do a greedy walk: from where you are, hop to the neighbor closest to the query; repeat until no neighbor is closer (a local minimum). Like finding someone across the country by always jumping to the friend nearest the target.

Small world, skip lists & the hierarchy jargon

A small-world graph lets you reach anywhere in few hops. HNSW borrows the skip-list trick — "express lanes" over a list turn O(n) into O(log n) — and stacks it into layers:

Layer 2 A ───────────────── E few nodes, LONG hops (express lanes) Layer 1 A ──── C ──── E ──── G more nodes, medium hops Layer 0 A─B─C─D─E─F─G─H (every node) short hops, fine detail

A node's height comes from randomLevel — a biased coin flip that decays exponentially (~1/M per level), so most nodes sit only on layer 0 and few reach the top.

Beam search & ef jargon

Greedy keeps one node; beam search (Quiver's searchLayer) keeps the best ef candidates and a frontier to explore — so it doesn't get stuck and it returns top-k. ef is the beam width: bigger ef explores more → higher recall, slower. It's a query-time dial (change it per query, no rebuild).

Jargon: efSearch (query breadth) vs efConstruction (build breadth) · M = max neighbors per node.

Search & insert, end to end

Search: start at the top entry point, greedily descend the sparse upper layers (big jumps to get near), then one ef-wide beam search on layer 0 for the exact top-k. "Zoom in."

Insert: roll a level; descend from the top to that level; from there down to 0, beam-search + link to the M nearest (both directions); if taller than everything, become the new entry point.

Degree capping / pruning jargon

Every insert adds back-edges, so popular nodes accumulate unbounded neighbors → search slows toward O(n). pruneNeighbors caps each node at maxDegree (2·M on layer 0, M above), keeping only the closest. In testing this dropped a hub from 106 → 16 neighbors while recall barely moved.

🤔 Check yourself: why is HNSW ~O(log n), and what does raising ef cost you?
The hierarchy is ~log_M(n) layers tall; a search does a cheap greedy hop per upper layer + one beam sweep at the bottom, so work grows like log(n), not n. Raising ef explores more of the graph → higher recall but lower throughput (slower). It's the recall↔speed dial.

⑦ The HTTP server

Turning the library into a service anything can call.

REST / HTTP / JSON & handlers jargon

Clients talk over HTTP (the web's request/response protocol) sending JSON (text data format). Quiver exposes endpoints: POST /vectors, POST /query, GET /health. A handler is the function that runs for an endpoint — it gets an http.Request (the incoming call, a pointer — one shared object) and an http.ResponseWriter (where you write the reply, an interface — already reference-like).

Status codes & DTOs jargon

Status codes are the reply's verdict: 201 created, 200 ok, 400 bad request (client's fault — e.g. wrong dimension), 500 server error (your fault). 4xx = "you messed up," 5xx = "I messed up."

A DTO (Data Transfer Object) is a struct describing the wire shape, e.g. addRequest{ID, Vector}. Struct tags (`json:"id"`) map JSON keys to Go fields — decoupling the public API name from the Go name.

Jargon: marshal = Go→JSON · unmarshal/decode = JSON→Go.

🤔 Check yourself: a client sends a 2-dim vector to a 3-dim index. 400 or 500?
400. The client sent malformed input — their fault. 500 is reserved for unexpected server failures. Choosing the right class is real API design: the caller can only see the status code, so it's how you communicate whose fault it is.

⑧ Concurrency

Many requests at once, without corrupting the index.

Goroutines & data races go

The HTTP server runs each request in its own goroutine (a lightweight thread). They all share one index. A data race = two goroutines touch the same memory, at least one writes, with no coordination → undefined behavior (corruption, crashes). Quiver's Add writes the graph while Search reads it → a race waiting to happen.

Mutex, RWMutex & the race detector go

A mutex (mutual exclusion lock) lets only one goroutine into a critical section at a time. An RWMutex allows many readers OR one writer — ideal for a read-heavy search index: searches run concurrently, a write briefly blocks everyone. Go's race detector (go test -race) instruments memory to catch races at runtime — Quiver's tests run clean under it.

🤔 Check yourself: why RWMutex instead of a plain Mutex here?
Searches are read-only and vastly outnumber writes, and readers don't conflict with each other. A plain Mutex would needlessly serialize every search (one at a time). RWMutex lets all those reads happen simultaneously and only blocks them briefly during a write — much higher throughput.

⑨ Persistence — the write-ahead log

Surviving a restart or crash.

WAL, fsync & durability jargon

The index lives in RAM — a restart wipes it. A write-ahead log (WAL) is an append-only file: every Add is written to disk (one JSON line) and fsync'd before it's considered done. fsync (Go's File.Sync()) forces the bytes onto durable storage instead of an OS buffer that a crash could lose — that's durability.

Replay & crash recovery jargon

On startup, Quiver replays the log — re-applying every logged Add — to rebuild the exact index. So a hard kill loses nothing: the writes are on disk, and replay restores them. (A future snapshot would bound how much log you must replay.)

Wiring: PersistentIndex is a decorator (§5) — it logs writes, replays on open, and delegates the rest. The server can't tell it's persistent.

🤔 Check yourself: why does Append call Sync(), and what breaks without it?
Sync() = fsync = force the write to actual disk. Without it, the OS may hold the data in a buffer; a crash before the flush loses that write even though the call "succeeded." Sync is what makes the log durable — the whole point of a write-ahead log.

⑩ Benchmarks & evaluation

Proving it works — with numbers, not vibes.

recall@k, QPS, latency jargon

recall@k = accuracy (fraction of true top-k found). QPS = queries per second (throughput). latency = time per query (ms); often reported as percentiles (p50 = median, p99 = "99% are faster than this"). Good search = high recall AND high QPS AND low latency — usually a tradeoff you tune.

Ground truth, SIFT & the Pareto curve jargon

Ground truth = the known-correct answers. SIFT is a standard benchmark dataset that ships ground-truth neighbors, so recall is measured against a trusted reference (not your own index). Quiver on SIFT10K:

ef recall@10 throughput 16 0.919 16,100 QPS 64 0.988 5,000 QPS 128 0.990 2,470 QPS 256 0.990 960 QPS

That's a Pareto / tradeoff curve: each ef is a different balance of accuracy vs speed. Retrieval + evaluation is exactly what AI-infra interviews probe.

🤔 Check yourself: say "0.99 recall@10 at 5,000 QPS" in plain English.
"For a typical query, we return about 9.9 of the 10 genuinely-closest vectors, and we can handle roughly 5,000 such queries per second on one CPU thread." High accuracy, high throughput.

⑪ Go concepts you used

The language mechanics that showed up.

The grab-bag go

slice a growable view over an array ([]T); append returns a (possibly new) slice — you must reassign it.

pointer &x = "address of x"; *T = "pointer to T". You pass a pointer so a function can modify your variable (e.g. json.Decode(&req) fills req).

pointer vs value receiver methods on *T can mutate the struct; on T get a copy.

error values errors are ordinary return values; compare with errors.Is; define sentinels like ErrDimMismatch.

struct tags `json:"id"` — metadata steering JSON encode/decode.

defer runs a call when the function returns (e.g. defer mu.Unlock()) — guarantees cleanup on every path.

exported vs unexported Capitalized = public across packages; lowercase = private to the package.

flag stdlib command-line flags — all must be declared before flag.Parse().

table-driven tests list cases in a slice, loop with t.Run; the idiomatic Go test style.

⑫ End-to-end flow (everything, in order)

Follow one insert and one query all the way through.

INSERT — POST /vectors
curl POST /vectors {id, vector} └─ server handler: decode JSON into addRequest (DTO) [⑦] └─ PersistentIndex.Add [⑨ decorator] ├─ idx.Add(...) → HNSW insert: [⑥] │ roll randomLevel → descend from entry (greedy) │ → beam-search each layer → link M nearest │ → pruneNeighbors (cap degree) → maybe new entry │ (RWMutex write-lock guards it) [⑧] └─ WAL.Append(record) → fsync to disk [⑨ durability] └─ respond 201 Created [⑦ status code]
QUERY — POST /query
curl POST /query {vector, k} └─ server handler: decode JSON into queryRequest (DTO) [⑦] └─ Index.Search(query, k) → HNSW: [⑥] Phase 1: from top entry, greedy-hop down sparse layers (get near) Phase 2: ef-wide beam search on layer 0 (get exact top-k) each hop scores with the metric (cosine/L2) [③] (RWMutex read-lock — many queries at once) [⑧] └─ map hits → results, encode JSON, respond 200 [⑦]

⑭ Final self-test

If you can answer these out loud, you can defend the whole project in an interview.

1. Walk an insert from curl to disk.
Handler decodes JSON→DTO → PersistentIndex.Add → HNSW insert (randomLevel, greedy descent, beam+link M nearest, prune, maybe new entry) under a write lock → WAL.Append + fsync → 201. (§12)
2. Why is HNSW faster than FlatIndex, and what's the catch?
Hierarchy → ~log(n) nodes examined vs O(n). Catch: it's approximate (recall < 100%), tuned by ef. (§4, §6)
3. Retrieval correctness vs semantic relevance — the difference?
Quiver's job is to return the true nearest vectors by the metric (retrieval correctness). Whether those are useful depends on the embedding model + corpus (semantic relevance). A weak result is the data/model's fault, not the index's.
4. Why RWMutex, and what proves it's correct?
Read-heavy workload → many concurrent reads, exclusive writes. go test -race proves no data races. (§8)
5. What makes the WAL durable, and how does recovery work?
fsync on every Append forces bytes to disk; on startup, replay re-applies every record to rebuild the index. (§9)
6. What does raising ef do to recall, QPS, and the graph?
↑recall, ↓QPS; the graph is unchanged (ef is a query-time dial). (§6, §10)
